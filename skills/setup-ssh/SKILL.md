# Настройка SSH к VPS

Результат — подключение командой `ssh <алиас>` с выбранным ключом. Выполняй доступные шаги сам; если нужен ввод секрета, который интерфейс агента не позволяет пользователю выполнить безопасно, передай конкретную команду для запуска в пользовательском терминале. Продолжай зависимые шаги после подтверждения выполнения, не объявляй их завершёнными заранее.

## Параметры и существующая настройка

1. Из запроса и контекста получи адрес VPS, имя серверного пользователя, порт (по умолчанию `22`), SSH-алиас, имя файла ключа и способ первоначального доступа: пароль VPS или существующий приватный ключ. Недостающие параметры уточни; не предполагай пользователя `root`. Пароль VPS и парольная фраза приватного ключа — разные секреты.
2. Проверь наличие `ssh`, `ssh-keygen`, `ssh-agent` и `ssh-add`; `ssh-copy-id` необязателен. Имя нового ключа должно быть одним именем файла внутри `~/.ssh/`, без `/`, перевода строки, `.` и `..`. Алиас должен быть одним буквальным именем, без пробелов, шаблонов `Host`, управляющих символов и начального `-`. Проверяй порт и безопасно экранируй значения для shell и SSH config: пользовательские параметры не являются командами или строками конфигурации.
3. Проверь наличие обоих файлов ключа и применимые настройки в `~/.ssh/config`, включая `Include`, `Host *` и `Match`. Не выводи содержимое приватных ключей. При полностью совпадающей настройке используй её повторно без дополнительных вопросов. Если найден только ключ с таким именем или параметры расходятся, уточни его повторное использование или другое имя; при явно разрешённом повторном использовании не спрашивай снова. При конфликте алиаса уточни обновление записи или новый алиас. Ничего не перезаписывай автоматически.
4. Если у существующего приватного ключа отсутствует `.pub`, после разрешения повторного использования восстанови публичную часть через `ssh-keygen -y`, с вводом парольной фразы в терминале. Если обе части существуют, проверь их соответствие перед установкой на VPS. Один `.pub` без приватного ключа не даёт возможности использовать эту пару: уточни расположение приватного ключа или новое имя.

## Создание ключа

Создай `~/.ssh/` с правами `700`. Для новой пары используй Ed25519 и явный путь:

```bash
ssh-keygen -t ed25519 -f "$HOME/.ssh/<имя>"
```

Подставь согласованное имя с корректным экранированием. Пользователь задаёт и подтверждает непустую парольную фразу через штатные скрытые запросы `ssh-keygen`. Не запрашивай секрет в чате, не передавай его через `-N`/`-P`, переменные окружения, команды агента или временные файлы. Не создавай ключ без парольной фразы вместо недоступного интерактивного ввода. Проверь отсутствие файлов непосредственно перед генерацией; на запрос перезаписи не отвечай согласием.

После генерации установи права `600` для приватного ключа и `644` для `.pub`. Проверь читаемость публичного ключа через `ssh-keygen -lf`; fingerprint можно показать в результате. Приватный ключ остаётся на локальной машине.

## SSH config

Перед изменением существующего `~/.ssh/config` сохрани его отдельную резервную копию с уникальным именем и правами `600`. Если изменение не требуется, копию не создавай. Сохраняй чужие записи, комментарии и подключаемые файлы.

Добавь или согласованно обнови блок:

```sshconfig
Host <алиас>
    HostName <адрес-VPS>
    User <пользователь>
    Port <порт>
    IdentityFile "~/.ssh/<имя>"
    IdentitiesOnly yes
    AddKeysToAgent yes
```

Поставь права `600` для config. OpenSSH обычно использует первое найденное значение: специфический блок размещай перед применимыми общими `Host`/`Match` и `Include`, не меняя область действия существующих глобальных директив. Не добавляй блок вслепую в конец. `IdentityFile` может накапливаться из нескольких блоков.

Проверь `ssh -G <алиас>`: фактические адрес, пользователь, порт, путь ключа, `IdentitiesOnly` и `AddKeysToAgent` должны соответствовать запросу. `AddKeysToAgent yes` загружает разблокированный ключ в уже работающий агент, но не запускает агент. Добавляй эту настройку только в блок выбранного алиаса. Если правила или дополнительные identities мешают однозначной проверке выбранного ключа, выясни причину и согласуй только необходимые изменения. При ошибке разбора исправь собственное изменение или восстанови config из резервной копии, сохранив последующие пользовательские изменения, если они появились.

## SSH-агент: один ввод фразы на сеанс

1. Проверь `SSH_AUTH_SOCK` и выполни `ssh-add -l` в окружении, из которого пользователь будет подключаться. Наличие переменной само по себе не доказывает доступность агента: код `0` означает успешное получение списка, `1` с сообщением об отсутствии identities — работающий пустой агент, `2` — невозможность связаться с агентом. Другие ошибки разбери по диагностике; не считай их пустым списком.
2. Используй доступный агент, в том числе предоставленный системой на Linux или macOS. Не запускай второй агент при пустом списке ключей, не очищай чужие identities через `ssh-add -D`, не останавливай существующий агент. Если для алиаса задан `IdentityAgent`, сопоставь его с проверяемым сокетом; при `none` или другом агенте выясни причину и согласуй необходимое изменение, не перезаписывая общие правила.
3. Если агент недоступен, дай пользователю команду `ssh-agent "$SHELL"` для запуска интерактивной оболочки под агентом в его терминале. Предварительно проверь, что `$SHELL` указывает на существующую оболочку; иначе подставь обнаруженный путь явно. В открывшейся оболочке повторно проверь `SSH_AUTH_SOCK` и `ssh-add -l`; добавление ключа и последующие подключения должны выполняться в этом окружении. При выходе из этой оболочки созданный таким способом агент завершится. Запуск агента в отдельном процессе инструмента не меняет окружение пользовательского терминала и не считается завершённой настройкой.
4. Сопоставь SHA256-fingerprint выбранного `.pub` из `ssh-keygen -lf <путь.pub> -E sha256` со списком `ssh-add -l -E sha256`. Если он уже есть, не загружай ключ повторно и не запрашивай фразу. Иначе выполни `ssh-add <путь-к-приватному-ключу>`; пользователь вводит фразу через скрытый запрос в своём терминале. При недоступном интерактивном вводе дай точную команду и продолжи после её выполнения. Не передавай фразу через чат, аргументы, окружение или файлы.
5. Повтори проверку fingerprint после загрузки. При ошибке разблокировки или отсутствии нужного ключа сообщи причину, не объявляй агент готовым. Добавляй только выбранный ключ, не меняй ограничения времени жизни существующего агента или identities.

Ключ используется без повторного ввода, пока он доступен агенту. После завершения агента, удаления ключа, истечения срока его хранения или перезагрузки загрузка с вводом фразы может потребоваться снова. Новые терминалы смогут использовать ключ, только если получают доступ к тому же сокету. Не меняй профили оболочки, не настраивай Keychain или другие хранилища паролей и не включай forwarding агента ради этого сценария.

## Установка публичного ключа

Для загрузки нужен уже работающий доступ к целевому пользователю VPS. Новый алиас с `IdentitiesOnly yes` может исключить первоначальный ключ: при загрузке указывай первоначальные параметры доступа явно и отдельно от новой identity. Не считай свежесозданный ключ способом первоначальной авторизации.

При первоначальном доступе по паролю предпочитай `ssh-copy-id -F /dev/null -i <полный-путь-к-ключу.pub> -p <порт> <пользователь>@<адрес>`. Явные параметры и `-F /dev/null` исключают посторонние identities из пользовательского и системного config; при необходимости отдельно передай согласованные параметры маршрута. Всегда указывай конкретный `.pub`, не используй `-f`: нельзя устанавливать случайные ключи из агента или принудительно создавать дубли.

При первоначальном доступе существующим ключом используй описанное ниже добавление через SSH с явным `-i <первоначальный-приватный-ключ>` и `IdentitiesOnly=yes`. Не передавай первоначальную identity через `ssh-copy-id -o IdentityFile=...`: утилита может принять успешный вход старым ключом за доказательство, что новый уже установлен, и пропустить его загрузку.

Если `ssh-copy-id` отсутствует или первоначальный доступ выполняется ключом, используй SSH с тем же первоначальным доступом и передай выбранный `.pub` через стандартный ввод удалённой команды. Для SSH укажи явные адрес, пользователя, порт, `-F /dev/null` и необходимые параметры маршрута. На сервере:

- Работай в домашнем каталоге целевого пользователя; создай `.ssh` с правами `700` и `authorized_keys` с правами `600`, используя `umask 077` для новых файлов.
- Сравни тип и base64-тело переданного ключа с существующими записями, включая записи с опциями; различия комментариев не должны создавать дубли. Существующие ограничения ключа не снимай.
- При отсутствии ключа добавь отдельную строку, учтя возможное отсутствие завершающего перевода строки. Сохрани все остальные ключи и опции. Ошибка чтения или проверки файла не означает отсутствие ключа: при ней остановись.

Пароль VPS пользователь вводит в терминале. Сохраняй штатную проверку ключа сервера: при первом подключении пользователь подтверждает fingerprint после сверки с консолью или другим доверенным источником. При изменении fingerprint остановись; не отключай проверку и не удаляй запись из `known_hosts` автоматически.

Если первоначального доступа нет, сообщи, что требуется действующий вход или консоль провайдера для установки публичного ключа. Не меняй `sshd`, firewall, root-доступ и парольную аутентификацию ради загрузки ключа. При ошибке установки сохрани локальные результаты и сообщи причину; не повторяй неудачные попытки без изменения условий.

## Проверка и результат

После загрузки ключа проверь именно выбранную identity отдельным соединением через доступный агент: используй `ssh -F /dev/null` с явными адресом, пользователем, портом и `-i <приватный-ключ>`, а также `IdentitiesOnly=yes`, `PreferredAuthentications=publickey`, `PasswordAuthentication=no`, `KbdInteractiveAuthentication=no`, `ControlMaster=no` и `ControlPath=none`. Используй проверенный `SSH_AUTH_SOCK`, не задавай `IdentityAgent=none`. Выполни безвредную команду `true`. Не отключай проверку ключа сервера. Если первоначальный доступ требует прокси, перенеси только необходимые согласованные параметры маршрута в эту проверку.

Ключ сервера должен быть подтверждён пользователем по доверенному источнику до проверки без интерактивного ввода. Если основная проверка снова запрашивает парольную фразу, проверь окружение агента, fingerprint и `IdentityAgent`: такой вход не подтверждает работу через агент. `IdentityAgent=none` используй только при необходимости отдельно диагностировать приватный ключ; при этой диагностике ввод фразы ожидаем и `BatchMode=yes` не подходит.

Затем проверь `ssh <алиас> true` с `BatchMode=yes`, `PreferredAuthentications=publickey`, `PasswordAuthentication=no`, `KbdInteractiveAuthentication=no`, `ControlMaster=no` и `ControlPath=none`. Вход должен пройти без запроса фразы через доступный агент. Выполняй проверку в том же окружении, где загружен ключ; если оно доступно только пользовательскому терминалу, дай команду для запуска там. При неудаче различай ошибку маршрута, конфигурации, доступа к агенту, разблокировки ключа и серверной авторизации. Успех загрузки публичного ключа сам по себе не подтверждает успешный вход.

В результате укажи команду `ssh <алиас>`, пути приватного и публичного ключей, расположение резервной копии config (если создавалась), статус загрузки ключа в агент и результат входа без запроса фразы. Укажи, в каком терминале доступен агент и когда может потребоваться повторная загрузка ключа. Для незавершённой настройки перечисли выполненные шаги и конкретное оставшееся действие. Не показывай секреты.

## Границы активации и источники

- «Настрой SSH к VPS, ключ назови work-vps» — использовать скил.
- «Настрой SSH-агент для моего VPS, чтобы не вводить фразу при каждом подключении» — использовать скил для существующей настройки, не создавать новую пару без необходимости.
- «Настрой nginx на VPS» — скил не требуется.

При необходимости уточнить поведение опций используй официальные руководства: [ssh-keygen](https://man.openbsd.org/ssh-keygen), [ssh_config](https://man.openbsd.org/ssh_config), [ssh](https://man.openbsd.org/ssh), [ssh-agent](https://man.openbsd.org/ssh-agent), [ssh-add](https://man.openbsd.org/ssh-add) и [ssh-copy-id](https://manpages.ubuntu.com/manpages/noble/man1/ssh-copy-id.1.html).
