# Отправка изменений с pull request

Запрос на полный процесс включает создание ветки при необходимости, коммит, push и обычный PR. Не запрашивай повторное подтверждение этих шагов, если намерение и состав изменений ясны; обязательные разрешения среды сохраняются. Явные ограничения пользователя имеют приоритет: например, при просьбе отправить без PR пропусти его создание.

## Порядок работы

1. Проверь инструкции репозитория, текущую ветку, изменения рабочего дерева и индекса, remotes и upstream. Определи состав изменений по запросу и контексту; если он неоднозначен, уточни его. При detached HEAD остановись. Заранее проверь доступность GitHub CLI и авторизации для PR, чтобы сообщить известные препятствия до отправки.
2. До коммита выбери ветку по задаче и состоянию PR согласно разделу ниже. Для новой ветки прочитай и примени [create-branch](../create-branch/SKILL.md), явно передав актуальную целевую базу и выбранный remote. При необходимости перенеси только изменения текущей задачи.
3. Если есть относящиеся к задаче незакоммиченные изменения, прочитай и примени [create-commit](../create-commit/SKILL.md). При отсутствии таких изменений продолжи с существующими коммитами, не создавая пустой коммит. При ошибке коммита не переходи к отправке.
4. Проверь состав будущего PR согласно разделу ниже, затем прочитай и примени [git-push](../git-push/SKILL.md). Для новой ветки назначение — одноимённая ветка исходного remote, а не базовая ветка PR. Если коммиты уже отправлены, продолжи к PR. Если push не выполнен или результат не подтверждён, остановись до создания PR.
5. Прочитай и примени [create-pr](../create-pr/SKILL.md) для фактически отправленной ветки и репозитория. Верни существующий PR или создай обычный; draft — только по явной просьбе. Если разницы с базой нет, сообщи, что создавать PR не из чего.
6. Дай единый итог: локальная и удалённая ветки, хеш и сообщение созданного коммита либо отсутствие нового коммита, результат push, ссылка на PR и оставшиеся незакоммиченные изменения, если они есть.

## Выбор ветки до коммита

Определи задачу по запросу, контексту, изменениям и коммитам; имя ветки — подсказка, а не доказательство её назначения. Определи исходный remote и целевой репозиторий PR, учитывая fork. Явно заданная пользователем база имеет приоритет; иначе используй default branch целевого репозитория, а не фиксированное имя `main`. При неоднозначном назначении уточни его.

Проверь связанные PR через `gh pr list --state all --head <branch>` с явным `--repo` и полями `state`, `mergedAt`, `headRefName`, `headRepository`, `headRepositoryOwner`, `baseRefName`, `url`. Сопоставь исходный репозиторий и ветку. Если данных недостаточно, получи детали PR; ошибка запроса не означает отсутствие PR. Учитывай историю: завершённый старый PR не мешает продолжению более нового открытого PR той же задачи, но требует проверки состава изменений.

| Состояние | Действие |
| --- | --- |
| Текущая ветка — базовая ветка целевого репозитория | Создай новую ветку для задачи. |
| Рабочая ветка относится к той же задаче, PR открыт или PR ещё не было | Продолжи текущую ветку; открытый PR не обязателен. |
| Ветка относится к другой задаче либо последний соответствующий PR merged или closed без мержа | Создай новую ветку от актуальной целевой базы. |
| Связь ветки с задачей или история PR неоднозначна | Уточни до коммита и push. |

Отсутствие удалённой ветки не доказывает завершение задачи. Если пользователь явно просит продолжить завершённую ветку, покажи последствия для коммитов и diff нового PR и согласуй дальнейшее действие до отправки. Остальные явные указания пользователя по ветке и базе имеют приоритет; не заменяй их автоматически выбранными.

Для новой ветки обнови сведения о целевой базе через fetch из remote целевого репозитория и передай её актуальный remote-tracking ref в `create-branch`. При fork исходный remote для push и remote целевой базы могут различаться. Не требуй обновления локальной `main` или переключения на неё. При ошибке fetch или недоступной базе остановись, не используй старый HEAD как замену.

## Перенос изменений и состав PR

- Незакоммиченные изменения переноси обычным переключением, если Git позволяет. Не создавай автоматически stash или промежуточный коммит. Если переключение невозможно, сообщи причину и уточни дальнейшее действие.
- Если коммиты задачи уже находятся в старой ветке, выдели их до переключения и перенеси через cherry-pick в исходном порядке, только если их принадлежность задаче однозначна. Не переноси коммиты прошлой завершённой задачи: после squash merge они могут отсутствовать в истории базы, хотя их изменения уже включены.
- При смешанных коммитах уточни способ разделения. Если cherry-pick конфликтует или перенос блокируют незакоммиченные изменения, остановись и сообщи состояние; не выбирай разрешение конфликта, stash или откат самостоятельно.
- До push обнови сведения о базе через fetch и проверь все коммиты относительно неё и diff от общей базы будущего PR, например `git log <base>..HEAD` и `git diff <base>...HEAD`. При ошибке обновления остановись. Проверки только последнего коммита или разницы конечных деревьев недостаточно. Для существующего PR используй его фактическую базу, согласованную с запросом пользователя.
- Если в состав попала неожиданная прошлая работа, остановись и выясни способ исправления до push. Пояснение в описании PR не заменяет исправления его состава. Если подходящих изменений нет, не создавай пустой коммит или PR.

Не дублируй правила подчинённых скилов; читай их перед соответствующим шагом. При ошибке сохраняй уже достигнутый результат и сообщай, какой шаг не выполнен. Не откатывай коммит или отправленную ветку из-за ошибки PR. Не выполняй автоматически amend, обход hooks, force push, merge, rebase или reset. Старые локальные и удалённые ветки не удаляй, PR не закрывай без отдельного запроса.
